Demande de l'utilisateur le 19/07/2026 : automatiser les messages en phonie (contest/expédition) — taper un indicatif dans la saisie QSO déclenche un message vocal (indicatif + report) synthétisé et émis PAR LA RADIO (pas les haut-parleurs PC), en réponse automatique façon callbot. Choix faits via AskUserQuestion : synthèse TTS (pas des enregistrements phonétiques pré-faits) + PTT automatique via CAT (pas manuel).

**FAIT — commit c40d797.** `concours/radiocontest_voicekeyer.py` (nouveau module) : épellation phonétique OACI (`spell_callsign`, suffixes /P /M /QRP dits comme un mot), chiffres un par un (`spell_digits`, jamais "fifty-nine"), macros `{CALL}`/`{MYCALL}`/`{RST_SENT}`/`{RST_RCVD}`/`{NR}` (`{CALL}` = le CORRESPONDANT, volontairement l'inverse de la convention CW existante où `{CALL}` = l'indicatif propre — cohérent avec l'usage phonie réel de redire l'indicatif de l'autre station). TTS via `pyttsx3`/SAPI5 (100% hors-ligne, choisi pour la fiabilité en contest sans dépendance réseau). Lecture via `sounddevice.RawOutputStream` vers un périphérique choisi (câble virtuel vers l'entrée micro radio). PTT automatique autour de la lecture, dispatché sur les 3 modes CAT existants (natif/TCI/rigctld) via `_set_ptt()` — a nécessité d'ajouter `set_ptt()` dans les 3 modules CAT (`radiocontest_cat.py`, `radiocontest_tci.py`, `radiocontest_rig.py`), le PTT natif existait déjà au niveau driver mais n'était pas exposé au niveau module. Endpoint `/rig/voice` + UI : section CONFIG dédiée (périphérique/voix/débit + bouton test) et panneau CALLBOT dans LOGBOOK (visible en phonie, pas en CW). 27 tests unitaires (tout mocké, jamais de vrai TTS/audio/CAT dans les tests).

**Piège rencontré pendant la vérification (à retenir) : un hang de 30s sur `/rig/voice` via le serveur de preview N'ÉTAIT PAS un bug de code.** Hypothèse initiale (COM/threading — `pyttsx3`/SAPI5 nécessiterait une init COM par thread, incompatible avec `ThreadingHTTPServer`) réfutée par test direct : `send_voice_message()` appelé depuis un `threading.Thread` frais retourne en 0.3s, identique à un appel direct. La vraie cause : le process serveur de preview tournait depuis avant une compaction de contexte et avait accumulé un état bloqué (probablement un thread resté bloqué d'un essai précédent tenant un verrou global PortAudio/COM). **Fix : simplement redémarrer le process serveur.** Après redémarrage, `/rig/voice` répond en ~150ms à chaque appel, y compris via un vrai clic sur le bouton CONFIG et sur un macro-bouton CALLBOT du LOGBOOK. Leçon générale : face à un hang inexpliqué sur un serveur de preview qui tourne depuis longtemps, redémarrer le process AVANT de chercher un bug de threading/COM dans le code.

Vérifié en conditions réelles : bouton "Tester" CONFIG (clic réel, pas juste appel JS) + macro CALLBOT LOGBOOK (lit `inputCall`/`inputRSTsent` réels, POST `/rig/voice`, réponse correcte). 349+27 tests passent (suite complète, aucun F/E). Config live (`.server_config.json`, gitignoré) restaurée à son état d'avant-test après vérification (les clés `voicekeyer_*` ajoutées par un `saveConfig()` de test ont été retirées, pas laissées activées sans que l'utilisateur l'ait choisi).
