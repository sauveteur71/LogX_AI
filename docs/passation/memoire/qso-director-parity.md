**Lot structurant, item 10 — réseau ADIF générique — fait, commit 9705fd4, 19/07/2026. TOUS les items de la roadmap (rapide + moyen + structurant, 10/10) sont maintenant traités.** Recherche préalable (WebSearch + WebFetch de la doc officielle N1MM) pour identifier le VRAI protocole d'interop entre loggers de concours tiers plutôt que d'inventer un format "ADIF over UDP" qui n'existe nulle part : N1MM Logger+ diffuse chaque QSO en UDP XML `<contactinfo>` (port 12060 par défaut, doc officielle `n1mmwp.hamdocs.com/appendices/external-udp-broadcasts/`) — et DXLog.net l'implémente EXPLICITEMENT en option ("style N1MM") pour rester compatible avec les outils qui l'écoutent. C'est donc le format de facto, pas une invention. `radiocontest_adifnet.py` (nouveau) : parsing (`xml.etree.ElementTree`, pas de regex fragile) + construction du même XML, réglages (mode off/listen/send/both, port, IP cible/broadcast, nom d'appli), écouteur UDP (réception, même pattern bind/recvfrom/thread que `radiocontest_wsjtx.py`) et `broadcast_qso` (émission, fire-and-forget). Le concours (`contest`) d'un QSO REÇU reste celui configuré ICI (pas le `contestname` du logger tiers) — même choix de conception que le pont WSJT-X, pour que le scoring `rules_db` s'applique correctement. Émission branchée dans `add_qso_to_log` (même endroit que le push Club Log Live temps réel) ; réception démarrée à chaud via `/adifnet/state` (même pattern que `/wsjtx/state`). 16 tests, dont un round-trip complet contre un VRAI échantillon XML N1MM copié depuis la doc officielle. 332 tests au total.
**Vérifié en direct sur le serveur réel** (pas seulement mocké) : mode `send` activé via `/config/save`, un QSO de test ajouté via `/log/add` → `sent_total` de `/adifnet/state` passé de 0 à 1 puis 2 (confirme tout le chemin : lecture config → hook → construction XML → `socket.sendto` réel réussi). Démarrage de l'écoute (mode `listen`/`both`) confirmé sans erreur. **Limite d'environnement assumée** : la boucle auto-réception (notre propre broadcast reçu par notre propre écouteur, via le rebouclage local du broadcast UDP) n'a PAS pu être confirmée dans le bac à sable réseau du navigateur de test (`listening`/`last_seen` restés à `False`/`0` après un broadcast local) — plausible restriction réseau du bac à sable (même catégorie que la limite `window.open()` déjà documentée pour les layouts), pas un bug de code : la mécanique socket est identique à celle du pont WSJT-X déjà éprouvé en production. À confirmer par l'utilisateur avec un vrai N1MM/DXLog sur le même réseau local.
**Découverte de sécurité importante pendant cette vérification** : `/config/save` fait un **REMPLACEMENT COMPLET** de `.server_config.json` (`current_config = cfg` puis écriture, radiocontest_http.py ~ligne 1751), PAS une fusion. Un POST partiel du type `fetch('/config/save', {body: JSON.stringify({adifnet_mode: 'both'})})` — fait par erreur pendant cette vérification pour "juste changer un champ" — a RÉELLEMENT écrasé toute la config réelle (indicatif, locator, mots de passe, clé API...) par ce seul champ, silencieusement (réponse `{"ok":true}` normale). Repéré immédiatement par la discipline de sauvegarde systématique + diff avant/après, restauré sans perte réelle. **Ceci généralise et explique mécaniquement** toute la famille d'incidents "carte.html/configuration.html reposte un localStorage périmé" déjà documentée plus haut : ces pages envoient toujours un objet de config COMPLET reconstruit depuis le formulaire, donc un POST partiel n'est jamais censé arriver en usage normal — mais ça veut dire que **toute vérification manuelle via `fetch('/config/save', ...)` doit TOUJOURS envoyer l'objet de config complet, jamais un patch partiel**, sous peine d'effacer silencieusement tout le reste. Règle ajoutée à la discipline de vérification pour toutes les sessions futures.
